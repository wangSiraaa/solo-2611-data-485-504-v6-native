# 定时器与输出水位联动修复

单进程、整数时间的同步实现。三个模块保留材料中的三个公共调用场景：

| 模块 | 公共能力 | 不依赖的组件 |
| --- | --- | --- |
| `timers.py` | `TimerService`：键控事件时间定时器，可被不使用水位的客户直接调用 | 与水位完全无关 |
| `watermarks.py` | `WatermarkTracker`：来源水位 + owner hold 前沿，非定时器生产者可独立使用 | 不依赖定时器 |
| `stream_operator.py` | `BatchOperator` / `StrictSink`：把两者连成加工链 | 组合上述两者 |

## 运行

需要 Python 3.11，无第三方依赖。

```bash
python3 probe.py     # 材料自带的固定观察场景，全部 actual == expected
python3 verify.py    # 26 个确定性场景 + 定时器差分模糊(300 种子) + 端到端算子模糊(200 种子)
```

## 原实现的三个缺陷与修法

1. **定时器替换/删除后旧登记仍触发。** 堆里没有墓碑概念，`set`
   同身份后旧条目仍在堆中并会被弹出执行；`delete` 只删了活动表。
   修法：堆条目带单调登记序号，`_active[identity]` 只指向当前 live 条目；
   弹出时若身份已无映射或序号不匹配即为墓碑，跳过。替换拿到新序号，
   天然是一次全新登记（新登记顺序），旧登记永远无法影响后来同身份登记。
2. **多 owner 持有相同 hold 时间被互相释放。** 旧实现用一个全局
   `set` 存时间，任一 owner 释放就把该时间从集合里删掉。
   修法：只保留 `owner -> timestamp` 映射，前沿直接对映射的 value 取 min，
   不同 owner 即使持有相同时间也是独立条目；同 owner 替换为原地改写后只
   刷新一次前沿，替换过程中不可能公开越过新 hold 的临时水位。
3. **输入水位直接公开，尚未交付的结果被判迟到。** 旧算子在回调里先
   release hold 再写 sink，且 advance 先推来源水位。修法见下。

## 定时器所有权方案（BatchOperator）

* **每次登记一个独立 hold，而不是每个身份一个。** hold 的 owner 用唯一
  token `(identity, serial)`。`schedule` 同身份替换时，新登记先拿到自己的
  hold，旧登记的 token 不再是 live token，但其 hold 仍受保护，直到定时器
  服务在某轮 `advance` 中实际扫过旧堆条目（以旧 deadline 为界，存放在
  `_tombstones` 小顶堆里，到点才 release）。
* **删除立即释放。** `delete` 后该登记不可能再产出记录，没有需要继续保护
  的东西，故先在定时器服务里摘除，再立即释放自己的 token，不触碰任何
  其他登记的 hold。
* **回调重入安全。** 触发顺序固定为：① hold 仍在保护时把记录交给 sink；
  ② 执行 `after_emit`，其中的新增/重设/删除全部落地，新登记在此期间已取得
  自己的 hold；③ 最后才释放本次登记的 token。回调里同身份再登记时，
  `_tokens` 已指向新 token，旧清理只 release 旧 token，删不到新保护。

边界：hold 以"登记"为粒度意味着替换会短暂存在两个 hold，受 20 key ×
每 key 至多 4 个有效定时器的规模约束，墓碑堆与全量扫描都很小；
`schedule` 先取 hold，若时间戳低于已公开水位会由 tracker 拒绝且不留状态。

## 关键场景：deadline=90 / output_timestamp=20，输入水位推到 100

sink 实际收到的事件顺序（`verify.py` 中断言）：

```
['watermark', 20]   # hold 把前沿钳在 20，来源虽到 100 也不能越过去
['record', 20, 'late-unless-held']   # 记录先交付，此时 sink 水位只有 20
['watermark', 100]  # 回调与 hold 退休完成后，前沿才允许公开到 100
```

`StrictSink` 以 `timestamp < 当前水位` 判迟到，因此记录在水位 20 下合法
接收；仅放宽迟到判据无法得到这个顺序，必须靠 hold 生命周期。

## 验证覆盖

`verify.py` 中的确定性场景覆盖：

* 定时器普通触发、`(deadline, 登记顺序)` 排序、边界 `deadline == wm` 触发；
* 同身份替换（旧回调不触发、新登记周期独立）、删除抑制、重复删除；
* 回调删除本轮已到期未执行的邻居、回调同身份再登记、回调新增未来定时器；
* deadline 严格大于当前水位、`output_ts <= deadline`、水位回退拒绝；
* tracker 前沿公式、多 owner 同时间独立释放、hold 替换无瞬时越界、
  低于已公开水位的 hold 被拒绝且状态不变、来源单调与空来源拒绝；
* 算子普通交付、90/20→100 的精确下游顺序、替换保护、删除释放、
  回调再登记的 hold 不断链、回调删除到期邻居、多来源取 min、
  外部非定时器 owner 共存、到期窗口内替换不泄漏 hold。

模糊测试：定时器服务对照一个独立的朴素参考实现（全量排序扫描）做差分，
300 个种子逐事件比对；端到端算子 200 个种子随机混合推进/调度/替换/删除/
回调链，每步断言 StrictSink 零迟到、水位与 tracker 公开值一致、没有任何
记录被更高的前置水位越过，收尾后所有 hold 与定时器均排空。
